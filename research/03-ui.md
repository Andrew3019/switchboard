# 03 — UI: one state model, two surfaces

Research date: **2026-08-06**. Version numbers and maintenance data were pulled live from
PyPI, npm, crates.io and the GitHub API on that date, not recalled from memory. Where a
project is dead, the evidence is a date, not an opinion.

---

## Recommended stack

**The honest answer to the headline question: no. A single UI codebase that renders both a
real terminal UI and a real web UI does not exist in a form worth betting on in 2026.**
Everything that claims to do it either (a) renders a terminal emulator inside a browser
tab — which is not a web UI, it's a terminal on a website — or (b) shares the component
*model* but not the components, which means you write the views twice anyway.

So: **two thin front ends over one typed state model.** That is exactly what braindump
principle #2 implies — but in its honest form:

> Storing all state as JSON/YAML does **not** give you a portable UI. It gives you a stable,
> **renderer-agnostic contract** — the necessary precondition. The remaining cost is writing
> two views, and that cost stays low *only if the state never mentions presentation*.

### The stack

| Layer | Choice | Why |
|---|---|---|
| **Core model** | One typed schema, **types generated** for the front ends (ts-rs if Rust, Pydantic→JSON Schema if Python) | Vibe Kanban's `#[derive(TS)]` approach: the backend model *is* the frontend's type model, drift is impossible (§7.8) |
| **Runtime / PTYs** | **herdr** — don't build any of this | Already has `events.subscribe`, 26 typed events, `agent wait --until blocked`, worktrees, and 15+ agent CLI integrations (§8.1) |
| **State transport** | herdr socket → your daemon → **SSE** (graph + live state) · **polling** (status board) | Snapshot-on-connect + deltas, with herdr's `state_change_seq` as `Last-Event-ID` |
| **Web front end** | **React 19 + Vite + `@xyflow/react` 12.11 + `elkjs` 0.12** in a worker, Tailwind v4 + shadcn/ui | **Airflow 3.x independently chose this exact pair** in a from-scratch 2025 rewrite. Best-in-class nested nodes, MIT (§4, §7.5) |
| **Graph components** | Free `ui.reactflow.dev` shadcn registry — `node-status-indicator`, `labeled-group-node` | Vendored source you own; the "blocked"/"needs-review" variants are a 6-line diff (§4.4) |
| **Terminal front end** | **Ratatui** + **`ascii-dag`** (if the daemon is Rust) | `ascii-dag` has a headless layout IR feeding *both* TUI cells and SVG — the only genuine "one layout, two surfaces" component found (§3.1) |
| **TUI placement** | A **herdr plugin pane** (`herdr plugin pane open`) | Sits *inside* the user's existing workspace next to the agent panes. Zero PTY code |
| **Terminal panes in the browser** | **wterm** (`@wterm/react`), not xterm.js — *only if you need them* | DOM-rendered, so find/copy/select/a11y work. xterm.js canvas breaks all of them (§2.1) |
| **Primary UI** | **The status board. Not the graph.** | See below — this is the highest-value finding in the report |

### Four decisions that matter more than the library choices

1. **Build the status board first; make the graph a drill-down from a board card.** Airflow's
   own docs call the *grid* "the primary interface"; Temporal deliberately shipped **no DAG at
   all**; Metaflow, Trigger.dev and Inngest ship **no graph library**. Vibe Kanban's shutdown
   post-mortem: *"engineers are spending more time planning and **reviewing**."* The review
   queue is the product (§7.4).
2. **Split "blocked" in two.** Airflow separates `DEFERRED` (purple — waiting on a machine)
   from `AWAITING_INPUT` (orange — waiting on a *human*) at the data-model level. herdr gives
   you one `blocked`; subdivide it in your layer. They route to different humans with
   different urgency (§7.1).
3. **Let each interrupt declare its own allowed actions.** LangChain's Agent Inbox ships
   `config: {allow_accept, allow_edit, allow_respond, allow_ignore}` per interrupt, and the UI
   renders only the permitted buttons. This is what keeps a status board **template-agnostic**
   — it needs to know nothing about your templates to render correct affordances (§7.2).
4. **Never put a UI schema in your YAML.** Widgets, widths, colors, column orders — keep them
   all out. The layer that looks like it enables both renderers is the one that ruins both
   (§5.4). This is the discipline the whole approach depends on.

### The tradeoff, stated plainly

You will write the graph panel and the status board **twice** — once in React, once in
Ratatui. Call it 2–4 weeks of duplicated view code. What you buy is a web UI that is actually
a web UI (deep links, real fonts, real copy/paste, responsive, shareable URLs) and a TUI that
is genuinely native and fast.

The alternative — Textual + `textual-serve` — saves that duplication and costs you the entire
quality of the web surface, because "web" there means *xterm.js rendering your TUI in a
browser tab*. For a product whose two headline panels are **a graph** and **an inbox**, that
is the wrong trade. (And `textual-web` has been untouched since **August 2024**; Textualize
Ltd was **dissolved in February 2026**. §1.1)

### Quick answers

- **Cheapest good-looking live agent graph:** React Flow 12 + elkjs + the free
  `ui.reactflow.dev` shadcn components, forked from their Workflow Editor template. An
  afternoon, $0. Not D3, not Cytoscape, not Mermaid (§4.4).
- **Transport:** **SSE** for the graph and live agent state; **plain polling** for the status
  board. WebSocket *only* for embedded terminal panes. Airflow — the largest orchestrator
  surveyed — polls for everything (§7.6, §8.2).
- **If you'd rather not run a JS build at all:** **Datastar** (v1.0.2, 11.75 KiB, official Go
  and Rust SDKs, SSE-native) + one graph island. A real fork in the road — see §5.6.

## 1. Frameworks that natively do both terminal and web

### 1.1 Textual + textual-serve / textual-web — the flagship candidate, and it fails

This was the obvious first choice and it does not survive contact with the evidence.

**Maintenance reality (GitHub API + PyPI, 2026-08-06):**

| Package | Latest | Released | Repo last push | Verdict |
|---|---|---|---|---|
| `textual` | 8.2.8 | 2026-06-30 | 2026-07-11 | **Healthy.** 36.9k stars, MIT |
| `rich` | 15.0.0 | 2026-04-12 | — | Healthy, MIT |
| `textual-serve` | 1.1.3 | 2025-11-01 | 2025-11-01 | **Maintenance-only.** Last *code* change 2025-04-16 ("bump textual.js"); the Nov 2025 commit is literally titled "version bump". 397 stars, 22 open issues |
| `textual-web` | 0.8.0 | **2024-08-30** | **2024-08-30** | **Dead.** Two years untouched, still self-describes as "beta". 1.4k stars, 22 open issues |

**The company is gone.** Textualize Ltd announced wind-down in May 2025
([blog](https://textual.textualize.io/blog/2025/05/07/the-future-of-textualize/)) and was
formally **dissolved 17 February 2026** (UK Companies House, SC718360). Will McGugan
continues to maintain Textual and Rich personally. That's fine for the *TUI* framework —
it's mature and battle-tested. It is not fine for the web-serving layer, which was the
commercial bet and is now the least-loved part of the tree.

**The architecture is the real problem, not the maintenance.** People assume Textual
"renders to the web." It does not. From
[Towards Textual Web Applications](https://textual.textualize.io/blog/2024/09/08/towards-textual-web-applications/):
interaction happens in the browser "with a terminal rendered using **xterm.js**". The
server spawns your app as a subprocess and pipes it over a WebSocket into a terminal
emulator in a browser tab.

So "renders in a browser" means: **a screenshot-accurate terminal, on a web page.** You get
a monospace grid. You do not get a web application. Concretely, what you lose:

- **No URLs.** "Linking to a specific view" is an *open issue* (textual-serve #26). You
  cannot link a teammate to a blocked workflow. For a status board whose job is "what needs
  me right now," this is disqualifying.
- **Broken paste.** "Unable to paste text into any Textual input via ctrl+v"
  (textual-serve #32) — open.
- **Font roulette.** "Nerd Font" (#31) open; xterm.js has long-standing web-font bugs
  ([xterm.js #1164](https://github.com/xtermjs/xterm.js/issues/1164),
  [#1534](https://github.com/xtermjs/xterm.js/issues/1534)).
- **Broken behind a path prefix.** "Static asset URLs use absolute host:port causing 404"
  (#28) — so mounting it under a reverse proxy or subpath is a fight.
- **Can't set the page title** (#39). Open.
- **Mobile is bad.** xterm.js copy/paste on touch devices is a known, unfixed problem
  ([xterm.js #3727](https://github.com/xtermjs/xterm.js/issues/3727)).
- **No real graph.** Textual has an excellent `Tree` widget and `textual-plot` (Feb 2026)
  for charts. It has **no DAG/graph widget**. You'd build the graph panel from scratch in
  character cells, and then that hand-built character-cell graph is *also* what your web
  users see. You'd be shipping ASCII art to a browser that can render SVG.

**One bright spot:** [`textual-serve-asgi`](https://github.com/uriyyo/textual-serve-asgi)
0.2.1 (2026-04-13) is a community ASGI adapter that lets you mount a Textual app inside
FastAPI/Starlette and ships a newer xterm.js. It's a good fix for the *deployment* gap
(upstream textual-serve is standalone-only). It does not fix any of the above; it's a
third-party package at 0.2.x maintained by one person.

**Verdict: use Textual if you want a Python TUI. Do not use it as your web strategy.**
The one scenario where it wins: if the web UI is genuinely just "occasionally check on
things from another machine" and you'd otherwise ship no web UI at all. Given the braindump
explicitly wants a graph panel and a status board in a browser, that's not this project.

### 1.2 Equivalents in other languages

Nothing better exists, and most of what claims to exist is the same xterm.js trick.

- **Charm's Wish** (Go, 5.4k stars, active 2026-07-31, MIT) — serves Bubbletea apps over
  **SSH**. This is a real and underrated "one app, multiple surfaces" story, and it's the
  most honest one in this report: the second surface is *another terminal*, and it says so.
  `ssh workflows.local` and you get the TUI. Multiplayer sessions work. Great for remote
  access; **not a web UI**. Worth knowing about as a bonus feature, not as the answer.
- **Vue TUI** (`Simon-He95/vue-tui`) — Vue 3 components with both a browser-DOM renderer
  and a CLI stdout renderer. This is the closest thing to a literal answer to the question.
  But: it renders *terminal-style* UI to the DOM (ANSI in a web page), so the web surface
  still looks like a terminal; and it's a single-maintainer project. Interesting, not
  bankable.
- **SvelTUI** (`RLabs-Inc/sveltui`) — Svelte 5 → terminal. Same shape as OpenTUI. Early.
- **r3bl-open-core** (Rust) — TUI + some web ambitions. Niche.
- **charmed_rust** — a Rust port of the Charm ecosystem. Unofficial, early.

## 2. Terminal-to-browser bridges

If the goal is "put an agent CLI pane in a browser," this is a solved problem — just not
the way most people think.

| Project | Stars | Last push | License | Notes |
|---|---|---|---|---|
| **xterm.js** (`@xterm/xterm` 6.0.0, 2025-12-22) | 21.0k | 2026-08-05 | MIT | The incumbent. Canvas/WebGL renderer |
| **wterm** (`@wterm/core` 0.3.2, 2026-08-02) | 3.4k | **2026-08-07** | Apache-2.0 | Vercel Labs. **DOM renderer.** See below |
| **ttyd** | 12.2k | 2026-06-30 | MIT | C + libwebsockets. The healthy standalone bridge |
| **wetty** | 5.4k | 2026-07-31 | MIT | Node + xterm.js. Alive |
| **gotty** (`sorenisanerd` fork) | 2.5k | 2026-08-05 | MIT | Use this fork; `yudai/gotty` original is stale |
| **Zellij** | 34.7k | 2026-08-05 | MIT | Ships its own web client — see below |

### 2.1 wterm is the important 2026 development

[vercel-labs/wterm](https://github.com/vercel-labs/wterm) renders the terminal **to the
DOM as HTML**, not to a canvas. Core is Zig compiled to WASM (~12 KB), with an optional
`@wterm/ghostty` backend (~400 KB) that is literally libghostty for full VT compliance.
Dirty-row tracking + `requestAnimationFrame` for redraws.

Why this matters: every complaint in §1.1 about xterm.js — copy/paste, Cmd+F find, text
selection, screen readers — is a consequence of painting text into a canvas where the
browser can't see it. DOM rendering makes all of those work for free. There's a first-party
`@wterm/react` package with a `useTerminal` hook and WebSocket transport built in.

Caveat: 0.3.2, 68 commits, Vercel Labs (i.e. explicitly experimental). Don't build the
product on it, but if you embed terminal panes in the web UI, start here rather than
xterm.js, and keep the swap cheap.

### 2.2 Zellij's web client is the precedent to study

Zellij 0.43.0 (Aug 2025) shipped a [web client](https://zellij.dev/documentation/web-client.html);
0.44.0 (Mar 2026) added remote sessions and Windows support. Architecture: an **axum web
server embedded in Zellij itself**, two WebSocket connections (one control, one terminal
data), HTTPS + auth enforced, **off by default**. Sessions are bookmarkable URLs.
[Aram Drevekenin's writeup](https://poor.dev/blog/building-zellij-web-terminal/) is worth
reading in full — it's the same problem you have.

The lesson: a terminal workspace manager can expose its panes over HTTP without becoming a
web framework. herdr is architecturally the same kind of thing. If herdr ever ships this,
you get browser panes for free.

### 2.3 The honest comparison: stream a TUI vs. render natively

| | Stream TUI into browser (xterm.js/ttyd) | Render natively in browser (React) |
|---|---|---|
| Effort | Near zero | You write the view twice |
| Looks like | A terminal | A web app |
| Deep links | No | Yes |
| Copy/paste | Broken-ish (canvas); fine with wterm | Native |
| Find (Cmd+F) | No (canvas); yes with wterm | Native |
| Responsive / mobile | Poor | Good |
| Retina / fonts | Fragile | Native |
| Accessibility | Poor (canvas) | Good |
| Graph rendering | Character cells only | SVG/canvas, real layout engines |
| Multiple viewers | Shared cursor / fights over one session | Independent |

**The decisive row is the last two.** Your two headline panels are a *graph* and a
*board*. Both are exactly the kind of thing character cells are worst at and the DOM is
best at.

**Conclusion:** use the bridge for what it's genuinely good at — **embedding live agent CLI
panes** (which really are terminals and should look like terminals) — and render the graph
and board natively. That hybrid is the right answer and it maps perfectly onto herdr owning
the PTYs.

Notes that matter for this project:

- **blessed is dead.** Last npm publish September 2015. `blessed-contrib` (which has the
  graph widgets people cite) last published February 2022. Do not start here in 2026.
- **OpenTUI** (moved to `anomalyco/opentui`) is the most interesting newcomer: a Zig
  rendering core via Bun FFI, Yoga flexbox layout, and **React and Solid reconcilers**. It
  fixes Ink's 30fps cap and memory profile. Production use: opencode, terminal.shop. At
  0.5.1 it's young but moving fast.
- **No TUI framework has a good DAG/graph widget.** Trees, yes, universally. Graphs, no.
  The exceptions are small crates: `tui-nodes` (Ratatui, niche) and — much more
  interesting — **`ascii-dag`**.

### 3.1 `ascii-dag` is the sleeper find

[`ascii-dag`](https://lib.rs/crates/ascii-dag) 0.10.0 (2026-08-03), Rust, **zero
dependencies**. Implements Sugiyama layered layout tuned for fixed-width terminals. Handles
diamonds, cycles, skip-level edges. Crucially, two properties this project needs:

1. **Subgraphs / clusters.** `add_subgraph()`, `put_nodes()`, `put_subgraphs()`, with cycle
   checking on nesting. That is *exactly* the controller → sub-controller → agent nesting
   from the braindump.
2. **Headless layout IR.** `compute_layout()` returns positioned nodes and routed edges,
   decoupled from painting: *"it also works as a plain layout engine — you can draw with
   Canvas, SVG, or your own widget."*

That second point is the only real "one thing, two surfaces" component in this entire
report. If the daemon is Rust, you can run one layout engine and paint the result to
Ratatui cells in the terminal *and* to SVG in the browser, guaranteeing the two views agree
about topology. Worth prototyping early — it's a small bet with a large payoff.

### 3.2 The React-everywhere fantasy

The tempting idea: write React once, render with `react-dom` on web and Ink/OpenTUI in the
terminal. **This does not work,** for the same reason React Native doesn't let you ship web
components to iOS.

Ink and OpenTUI are React *reconcilers* with their own host components. Ink gives you
`<Text>`/`<Box>`; OpenTUI gives you `Box`, `Text`, `Input`, `Select`; the DOM gives you
`<div>`/`<span>`. They are not interchangeable, and none of your CSS, event handling, or
DOM APIs transfer. OpenTUI's own docs say code sharing is "very limited."

What you *can* share is real but modest, and it's the React Native `.web.tsx` / `.tui.tsx`
pattern:

- ✅ TypeScript types generated from your JSON/YAML schema
- ✅ State stores, selectors, derived state ("which workflows are blocked")
- ✅ Data fetching / event-stream client
- ✅ Pure formatting and sorting logic
- ❌ Every actual view

That's worth having — it's the "one state model" half of the recommendation — but it is
**not** "one UI." Be clear-eyed: if you pick Ink/OpenTUI for the TUI purely to share React
with the web app, you are buying about 30% sharing at the cost of running your daemon's UI
layer on Node/Bun. Only do it if TypeScript is already your backend language.

### 4.2 The key empirical finding

ELK was benchmarked directly during this research. **ELK returns child coordinates
*relative to their parent* and auto-sizes parents around their children — which is exactly
React Flow's `parentId` contract.** No coordinate transformation is needed. That single
fact is why this pairing beats libraries with "built-in" grouping.

```
grpA:  x=66.67  y=168   width=192  height=180   <- parent auto-sized by ELK
  a1:  x=16     y=48                            <- RELATIVE to grpA
  a2:  x=16     y=116                           <- RELATIVE to grpA
```

`width=192` = `padding.left 16 + child 160 + padding.right 16`.

**Measured layout times** (Node 22, Apple Silicon, best of 3, warm):

| Nodes | `INCLUDE_CHILDREN` | `SEPARATE_CHILDREN` |
|---|---|---|
| 31 (5 groups × 5) | 21 ms | 13 ms |
| 111 (10 × 10) | **48 ms** | 24 ms |
| 221 (20 × 10) | **78 ms** | 38 ms |
| 481 (30 × 15) | 155 ms | 67 ms |

At your scale (tens to low hundreds), a **full** re-layout is 20–80 ms. Cross-hierarchy
edges and cycles both laid out correctly under `INCLUDE_CHILDREN` — so "graph, not strictly
a tree" is a non-issue.

### 4.3 Why not the others

|---|---|
| **Cytoscape.js** | Strong second, wrong shape. ### 4.4 The cheapest path to a *good-looking* graph

This is where React Flow wins outright. **`ui.reactflow.dev` is a shadcn registry of React
Flow components, all free/MIT, vendored into your repo as source you own:**

```bash
npx shadcn@latest add https://ui.reactflow.dev/base-node
npx shadcn@latest add https://ui.reactflow.dev/node-status-indicator   # your exact requirement
npx shadcn@latest add https://ui.reactflow.dev/labeled-group-node      # your exact requirement
npx shadcn@latest add https://ui.reactflow.dev/labeled-handle
npx shadcn@latest add https://ui.reactflow.dev/button-handle
npx shadcn@latest add https://ui.reactflow.dev/node-tooltip
```

`node-status-indicator` is literally a `loading | success | error | initial` wrapper, and
its `loading` "border" variant is a **conic-gradient rotating around the node's border** —
the animated-glow look from polished AI product UIs, free. Because the source lands in
*your* repo, adding `blocked` (amber) and `awaiting-review` (violet, pulsing) is a ~6-line

### 4.5 The gotchas that will cost you time

In rough order of pain:

1. **Parents must precede children in the `nodes` array.** Push parent → then recurse.
   Get it wrong and children render at absolute coords or vanish.
2. **ELK coords are parent-relative — do not "fix" them.** The most common failure is
   adding the parent's absolute position and flinging children off-canvas. Assign directly.
3. **Reserve the group header** via `elk.padding` `top=48`, matched to your component's
   title-bar height. Mismatch = children overlapping the title.
4. **Do not set `width`/`height` on group nodes going *into* ELK** — ELK computes them.
   Take them out of the result and write to both `width`/`height` *and* `style.width`/
   `style.height` (v12 wants the style for the DOM box).
5. **`hierarchyHandling: 'INCLUDE_CHILDREN'` is required for cross-group edges** and costs
   ~2× layout time. Worth it — with `SEPARATE_CHILDREN` your sideways edges route badly.
6. **Ignore ELK's `edges[].sections`.** Those routed polylines are relative to each edge's
   `container`. React Flow routes its own edges; just don't read them.
7. **`nodeTypes` must be module-scope or `useMemo`'d.** Recreating it remounts every node on
   every render. This is the #1 React Flow perf bug and it will present as *"the graph
   flickers on every status update."*
8. **Set `zIndexMode="auto"`** (added v12.10, Mar 2026). Default is `'basic'`; the docs say
   `'auto'` is "for selections and sub flows." It fixes classic nested-group z-fighting.
   Older tutorials that hand-manage `zIndex` are obsolete.
9. **Two-pass measurement.** ELK needs sizes before layout; React Flow measures after
   render. Simplest fix: hardcode uniform agent-card sizes.

### 4.6 The architectural rule that matters more than the library

**Split the update path in two. Status changes must be invisible to the layout engine.**

```ts
// topology fingerprint — cheap, stable, order-independent
const topoKey = useMemo(() => JSON.stringify([
  nodes.map(n => `${n.id}>${n.parentId ?? ''}`).sort(),
  edges.map(e => `${e.source}->${e.target}`).sort(),
]), [nodes, edges]);

useEffect(() => { runElkLayout(); }, [topoKey]);   // ONLY on structural change

// status / progress / badges NEVER touch layout:
const { updateNodeData } = useReactFlow();
sse.on('agent:state', ({ id, status }) => updateNodeData(id, { status }));
```

React Flow's `NodeWrapper` subscribes per-node via a Zustand selector with shallow equality,
so preserving object identity for untouched nodes gives a genuine **single-node re-render**.

This is the entire answer to "cheap partial re-render without relayout thrash," and it is a
property of *your code*, not the library. Stabilizers: set
`elk.layered.considerModelOrder.strategy: 'NODES_AND_EDGES'` to preserve the mental map
across re-layouts, debounce layout ~150 ms, and animate positions rather than snapping.

For comparison, Cytoscape's incremental API is honestly more elegant —
`cy.$id(id).data('status','running')` with stylesheet-driven repaint and `cy.batch()` — but
it doesn't buy back canvas rendering or the dead expand/collapse extension.

## 5. Server-driven / declarative UI protocols

### 5.1 AG-UI — the most relevant thing here, and it validates the architecture

[AG-UI](https://docs.ag-ui.com/) (CopilotKit, MIT, ~15.2k stars, early 2025) is an
event-based protocol for agent→app communication. Its event taxonomy is close to what
you'd invent anyway: `RunStarted/Finished/Error`, `StepStarted/Finished`,
`ToolCallStart/Args/End/Result`, and — the important ones —
**`StateSnapshot` / `StateDelta`** and `ActivitySnapshot` / `ActivityDelta`.

Transport-agnostic: SSE, WebSocket, or webhooks over plain HTTP. First-party TS + Python
SDKs; community **Go** and **Rust** SDKs. Integrations with LangGraph, CrewAI, Mastra,
Pydantic AI, the Claude Agent SDK, and more.

**Why it matters to you isn't the protocol — it's the proof.** `npx create-ag-ui-app`
scaffolds React, Next.js, Vite, **or terminal-only** targets. There's a
`apps/client-cli-example` in-repo and a community **Textual-based terminal client**, plus
Slack and Teams clients. The docs state the principle explicitly:

> *"the protocol describes an event stream rather than a rendering target."*

That is the single best external validation of the "two thin front ends over one state
model" recommendation. One event stream, N independently written renderers, shipped in
production. Nobody in that ecosystem is generating both UIs from one schema — because it
doesn't work.

**Should you adopt AG-UI?** Probably not as your primary protocol. Its event vocabulary is
chat/agent-run shaped (text deltas, reasoning traces, tool calls), while yours is
workflow-shaped (steps, templates, blocked-on-human, labels). Adopting it would mean
squeezing your domain into someone else's events. **But steal `StateSnapshot` +
`StateDelta`** — snapshot on connect, deltas thereafter — because that is exactly the right
pattern and it composes perfectly with SSE `Last-Event-ID` (see §8). Consider AG-UI later
as an *export* format if you want CopilotKit-style embedding.

### 5.2 MCP Apps / MCP-UI — now a real spec, but not your dashboard

The answer to "is there a standardized 'MCP server returns a UI' spec?" is now **yes**.
Timeline: community `mcp-ui` → SEP-1865 (2025-11-21) → shipped as **MCP Apps**, the first
official MCP extension, spec dated **2026-01-26**, folded into the extensions framework in
the **2026-07-28** MCP spec. Co-authored by MCP maintainers at **both Anthropic and
OpenAI** — the OpenAI Apps SDK and mcp-ui converged rather than fragmenting.

Mechanics: servers pre-declare HTML templates as resources under the **`ui://`** scheme
with mimeType `text/html;profile=mcp-app`; tools link them via `_meta.ui.resourceUri` and
declare `_meta.ui.visibility`. The view renders in a **sandboxed iframe** and speaks MCP
back to the host over a **JSON-RPC postMessage transport** (`ui/initialize`, `ui/message`,
`ui/request-display-mode`, host→view `ui/notifications/tool-result`, etc.). Hosts enforce
CSP and must block undeclared domains. Rendered today by ChatGPT, Claude, VS Code Copilot,
Goose, Postman, Shopify.

**Note:** `remote-dom` and `externalUrl` were **explicitly excluded from the MVP**. The
declarative-tree path everyone finds interesting is not standardized; HTML-in-an-iframe is.

**Relevance:** this is for *a chat host rendering a server's panel*. Zero terminal story.
Adopt it only if you want your workflow board to also appear inside Claude/ChatGPT — a nice
additive third client later, not your primary UI.

### 5.3 JSON Schema-driven UI

- **[JSON Forms](https://jsonforms.io/docs/architecture)** — architecturally the most
  interesting: `@jsonforms/core` is genuinely UI-technology-independent. It takes a **JSON
  Schema** (data shape) plus a **separate UI Schema** (layout), and renderers register in a
  registry with *testers* that rank themselves per element. Bindings for React/Angular/Vue.
  **No terminal renderer exists**, but it's the only library whose architecture would allow
  one.
- **rjsf / uniforms / Formily** — simpler or heavier variants, React-centric, no terminal
  story. (2026 maintenance for uniforms/Formily unverified.)
- **[`collective/tui-forms`](https://github.com/collective/tui-forms)** — the curiosity:
  JSONSchema-driven *terminal* form wizards with pluggable renderer backends (stdlib,
  `rich`, cookiecutter), explicitly inspired by rjsf. **~5 stars.** A proof of shape, not
  infrastructure.

### 5.4 ⚠️ The trap: do not put a UI Schema in your YAML

This is the most important warning in the report and it cuts against the instinct the
braindump expresses.

It is very tempting to conclude: "state is JSON, so let's also describe the *UI* in JSON —
widgets, layout, columns — and then any renderer can draw it." **Don't.** That layer looks
like it enables both targets and in practice prevents both. Terminal and browser want
genuinely different layouts (80 columns of character cells vs. a responsive SVG canvas),
so a shared UI schema collapses to a lowest common denominator that renders badly in each,
and every new feature requires extending a schema *and* two interpreters instead of just
writing the view.

JSON Forms gets away with it only because *forms* are the one domain where the two layouts
genuinely coincide.

**The rule:** keep `templates`, `labels`, `learnings`, and workflow state **strictly
semantic**. No widths, no colors, no widget names, no column orders. The moment presentation
leaks into the state files, the second renderer stops being cheap. Get this right and the
braindump's principle #2 is fully vindicated — just in its honest form:

> Storing all state as JSON/YAML does not give you a portable UI. It gives you a stable,
> **renderer-agnostic contract** — the necessary precondition. The remaining cost is writing
> two views, and that cost stays low *only* if the state never mentions presentation.

### 5.6 Datastar — the sleeper pick for a Rust/Go backend

[Datastar](https://data-star.dev/) v1.0.2, MIT, ~4.8k stars, **11.75 KiB total**. It began
as a proposed TypeScript rewrite of htmx and became its own thing with an **SSE-first**
posture, combining htmx-style server round-trips with Alpine-style local reactive signals
in one file.

Declarative attributes (`data-bind`, `data-on:click="@post('/x')"`, `$signal`); the server
pushes `PatchElements()` and `PatchSignals()` over SSE. **Backend SDKs include official Go
and Rust** (plus Python, Zig, and ~11 more).

Why it fits: your backend already emits JSON state over SSE. Datastar's model is literally
"server pushes DOM patches and signal patches over SSE." **No npm, no bundler, no build
step, no virtual DOM.** For the graph you mount one island (React Flow / Cytoscape) and
feed it JSON; Datastar handles all the surrounding chrome, tables, and live updates.

This is a genuine fork in the road, so state it plainly:

- **Datastar path** — cheapest possible web front end, no JS toolchain, backend-language-
  native. Cost: the graph panel is a hand-wired JS island, and you're on a 4.8k-star
  library rather than the industry default.
- **React + Vite path** — more setup (npm, bundler, ~30 deps), but React Flow is a
  first-class citizen rather than an island, and the component/example ecosystem is
  enormous.

Given that **the graph is a headline feature, not a detail**, the React path is
recommended — but if the graph turns out to be secondary to the status board (which §7
suggests it might!), revisit Datastar seriously.

## 6. "openui" — what the user meant

Four different things carry that name. Short answer: **they almost certainly meant Open
WebUI; the one you should actually use is none of them.**

### 6.1 Open WebUI — the likely referent, and a licensing trap

[open-webui/open-webui](https://github.com/open-webui/open-webui), ~148k stars. The LLM
chat frontend. Architecture is worth noting because it's a genuinely good pattern:
**SvelteKit/Svelte 5 SPA compiled and served by a single FastAPI process** that also serves
the REST API. Extension points: **Tools** (function calling), **Functions** (in-process
filters and "pipe" pseudo-models), and **Pipelines** (a separate OpenAI-compatible FastAPI
middleware server on :9099). Speaks MCP/MCPO.

**🚩 The license.** Through **v0.6.5** it was BSD-3-Clause. From **v0.6.6 (April 2025)** it
moved to a custom **"Open WebUI License" — explicitly not OSI-approved** — with a mandatory
branding clause: you may not alter, remove, or obscure "Open WebUI" branding (name, logo,
UI marks) in the header, sidebar, login screen, or About section, in any deployment or
distribution. Exemptions: ≤50 end users in a rolling 30-day period; substantive merged
contributors by written permission; or a paid enterprise license. Contributions now require
a CLA. This caused significant backlash and fork-from-v0.6.5 advocacy in late 2025.
([license docs](https://docs.openwebui.com/license/),
[discussion #8467](https://github.com/open-webui/open-webui/discussions/8467))

**Verdict: do not build on it.** Three reasons, in order of severity:
1. **Wrong data model.** It is a *chat* application — conversations, models, messages. Yours
   is workflow runs, templates, labels, and a state graph. You would fight it constantly.
2. **No seam for what you need.** Functions and Pipelines intercept the *model call path*.
   There is no extension point that means "render this workflow DAG."
3. **The license.** Even if you stay under 50 users, you inherit a non-OSI license and a CLA
   on a codebase you'd be heavily modifying.

**Steal the one good idea:** a single process that serves both a compiled SPA and the JSON
API. For a localhost tool, that's the right deployment shape — one binary, one port, no
CORS, no separate dev server in production.

### 6.2 OpenUI by Weights & Biases — dormant, and obsoleted

[wandb/openui](https://github.com/wandb/openui), 22.5k stars, Apache-2.0. Describe a UI in
English → it generates and live-renders HTML, then converts to React/Svelte/Web Components.
Not archived, but **effectively dormant**: last substantive commit `2025-09-15`; everything
in 2026 is Renovate/dependency chores. 89 open issues.

**Verdict: skip.** Irrelevant as a runtime, and obsoleted as a design-time tool — you have
Claude Code, which generates the same React with far better context about your actual state
schema. If the user's interest was "can AI generate my UI for me," the answer is yes, but
not via this.

### 6.3 open-ui.org — the W3C Open UI Community Group

Not software. A W3C CG that catalogs UI patterns and drives them into browsers natively.
Shipped: **Popover API**, **Invoker Commands**, **CSS anchor positioning**, **customizable
`<select>`** (Stage 3). In flight: Interest Invokers, Focusgroup, native combobox.

**Not what they meant, but quietly relevant:** in 2026 you can build menus, dropdowns,
tooltips, dialogs, and anchored panels with essentially zero JS component library. That
materially lowers the cost of the lightweight (Datastar / plain-HTML) option.

### 6.4 OpenUI5 (SAP)

Apache-2.0 open-source subset of SAPUI5, SAP's enterprise MVC toolkit. Fiori territory.
Not it.

## 7. How comparable tools solved this

Two structural facts reframe the whole brief:

1. **The "kanban board for coding agents" category is consolidating hard.** Vibe Kanban
   announced its **sunset on 2026-04-10** ("the vast majority are free users and we couldn't
   find a business model we could get excited about"); it continues as MIT community open
   source. Terragon now serves a shutdown page. Crystal was renamed Nimbalyst. HumanLayer
   pivoted off the approval-API product entirely. The survivors are attached either to an
   agent vendor (Cursor, Amp, Copilot, Codex) or to a durable-execution engine.
2. **Vibe Kanban's own post-mortem states your thesis:** *"As software increasingly automates
   the coding part of the job, software engineers are spending more time planning and
   **reviewing** code."* The review queue is the product. The graph is decoration.

### 7.1 The 2026 consensus visual language

Airflow 3.x's semantic token map (`airflow-core/src/airflow/ui/src/theme.ts`) is the closest
thing to an industry reference implementation:

```
success → green      queued → stone       skipped → pink
failed  → red        running → cyan       restarting → violet
up_for_reschedule → sky        up_for_retry → yellow
upstream_failed   → amber      deferred     → purple
awaiting_input    → orange   <-- human-in-the-loop
scheduled → zinc     none → gray          removed → slate
```

Cross-tool consensus:

| Semantic | Color | Motion |
|---|---|---|
| Done / success | green | static |
| Failed / error | red | static |
| Running / active | blue or cyan | animated (pulse / marching ants) |
| Queued / pending | gray / neutral | static |
| Retrying | yellow | animated |
| **Blocked on a *machine*** (deferred, waiting-for-event) | **purple** | dashed / animated |
| **Blocked on a *human*** | **orange / amber** | static, badged + counted |
| Skipped | pink or faded | de-emphasized |
| Upstream failed | amber (distinct from own failure) | static |

**Two refinements worth stealing outright:**

- **Temporal separates color from line style.** From their UI redesign writeup: *"Red means
  failure, dashed red means retrying, dashed purple is pending, green means completion,"* and
  *"when an Event is pending — awaiting on another Event — the line is dashed and animates
  forward."* Color = outcome; dash + motion = pendingness. Two axes on one glyph.
- **Airflow separates the two kinds of "blocked" at the data-model level**, not just visually:
  `DEFERRED` (purple, waiting on a trigger) vs `AWAITING_INPUT` (orange, *"parked waiting for
  human input"*) are distinct members of `IntermediateTIState`. In Airflow 3.3 `awaiting_input`
  is scheduler-managed and consumes **no worker slot and no pool slot** — the human wait is
  free.

**Adopt this split.** `blocked_on_system` (purple, dashed, animated) vs `needs_review`
(orange, solid, badged). Do not collapse them — they route to different humans with different
urgency. Note this is a refinement of herdr's single `blocked` state; you'll want to subdivide
it in your own layer.

### 7.2 The best "what needs ME right now" UI: LangChain's Agent Inbox

[`langchain-ai/agent-inbox`](https://github.com/langchain-ai/agent-inbox) (Next.js + shadcn)
is the reference implementation, and its types are worth copying nearly verbatim.

**Filter tabs, and note the default:**
```
All | Interrupted | Idle | Busy | Error
selectedInbox = searchParams.get(INBOX_PARAM) || "interrupted"
```
**The app opens on "Interrupted," not "All."** The needs-you queue is the home screen. That is
the single most important design decision in the product.

**The interrupt contract — copy this:**
```ts
interface HumanInterruptConfig {
  allow_ignore: boolean; allow_respond: boolean;
  allow_edit: boolean;   allow_accept: boolean;
}
interface HumanInterrupt {
  action_request: { action: string; args: Record<string, any> };
  config: HumanInterruptConfig;
  description?: string;   // markdown
}
type HumanResponse = { type: "accept" | "ignore" | "response" | "edit";
                       args: null | string | ActionRequest };
```
Four response verbs — **accept / edit / respond / ignore** — and crucially **the agent
declares which are permitted per interrupt**; the UI renders only the allowed buttons. This
means your board needs to know *nothing* about workflow templates to render correct
affordances. That is the key to a template-agnostic status board.

Their status pills deviate from the orange consensus: `interrupted` renders **green**, labeled
"Requires Action," because in an *inbox* needing-you is an opportunity to clear an item, not a
failure. Defensible — but in a board where it sits next to genuine failures, use orange.

Layout, from the component inventory: **list of items → detail pane → tool-call table → action
buttons.** It's an email client. Fetching is plain paginated `threads.search({offset, limit,
status})` driven by URL query params, so inbox views are linkable. **No streaming.**

### 7.3 Other patterns worth stealing

- **Airflow 3.1+ "Required Actions"** (Browse → Required Actions) — the best *centralized*
  queue in a classic orchestrator: all pending actions across the whole instance, cross-DAG.
  In 3.3+ you respond **from the list via a slide-out panel** without navigating away.
  Critical details: `assigned_users` scopes who may respond (**ship this day one**);
  `defaults` + `execution_timeout` auto-resolve on timeout — *an inbox that can never be
  drained is a bug*; `generate_link_to_ui_from_context` produces a **deep link straight to
  the response form** for Slack/email; the decision lands in XCom as data downstream steps
  consume.
- **Prefect's two-level state model** — `StateType` is deliberately tiny (`SCHEDULED, PENDING,
  RUNNING, COMPLETED, FAILED, CANCELLED, CRASHED, PAUSED, CANCELLING`) with richer *state
  names* (Late, AwaitingRetry, Suspended, Retrying) layered on top. **Board groups and colors
  by type; card text shows the name.** Copy this. Also: `pause_flow_run(wait_for_input=...)`
  takes a Pydantic model and the UI **auto-generates the form** from it.
- **Trigger.dev waitpoints** — `wait.createToken()` / `wait.forToken(id)` /
  `wait.completeToken(id, decision)`, statuses `WAITING / COMPLETED / TIMED_OUT`. The
  waitpoint is a **first-class addressable object independent of the run**, so approvals can
  be listed, assigned, deep-linked and expired without touching run state. **Model the block
  as an entity, not a boolean flag on the run.**
- **Windmill** — suspend steps mint per-approver **resume/cancel URLs** emailable to people
  with no account; supports **N-of-M approvals**.
- **n8n** — HITL wraps *tools on an agent node*, not special node types. On deny, **the AI is
  told it was rejected** and the rejection feeds back into the loop rather than being dropped.
- **Vibe Kanban's columns** are the state model: *To do / In progress ("an agent **or person**
  is actively working") / **In review** ("work is done and waiting for your review") / Done*,
  with Backlog and Cancelled behind an "All" tab.

### 7.4 Grid vs graph: the vendors now say it out loud

Your instinct is right, and this is the most decision-relevant finding in the report.

- **Airflow's own docs:** *"Grid View: **the primary interface** for inspecting DAG runs and
  task states."* The Graph view shows *"the **logical structure**… how tasks are connected."*
  Structure, not state.
- **Temporal deliberately did not build a DAG.** They shipped three *linear* views — Compact,
  Timeline, Full History. The enabling abstraction was **Event Groups**: related events
  collapse into one row so users *"get a fast yet accurate picture."*
- **Dagster** spent real engineering to make big graphs viable, and the fix was largely
  "render less graph." Swapping the dagre ranker from `network-simplex` (O(N³)) to
  `tight-tree` took a 2,000-asset layout **from several minutes to ~5 seconds**; layout runs
  in a **WebWorker**; results cached in **IndexedDB** (not localStorage — 10 MB cap, and a
  1,000-node layout is multiple MB) keyed by a SHA-1 of the layout inputs; edges render only
  when both endpoints are visible past 50 edges. Their day-to-day surfaces are still the
  **Runs list** and a **Gantt**.
- **Metaflow** is the cleanest signal: `Netflix/metaflow-ui` has React 18,
  `react-virtualized`, `reconnecting-websocket` — and **no graph library at all**.
- **Langfuse** shows the resolution rather than picking a side: their Agent Graph has an
  **Aggregated** mode (the shape of the agent, template-level) and an **Expanded** mode that
  *"reads closer to the trace tree — the right view when you want to follow a specific run
  end to end."* **Steal this toggle directly** — it maps exactly onto your "template" vs
  "in-flight workflow" distinction.
- **Amp's Thread Map** (Dec 2025) is explicitly *not* an execution graph: threads connected by
  mentions, handoffs and forks, to see "the **shape** of your work." They found two recurring
  topologies: **hub-and-spokes** and **chain**. Which is exactly what your controller →
  sub-controller → agent graph will look like — and it argues the graph is a low-information
  display most of the time.

**Conclusion: build the status board first. Make the graph a drill-down from a board card.**
The graph earns its place for three jobs only: (a) understanding a *template's* shape while
authoring, (b) locating *where* in a run something broke, (c) showing fan-out/handoff topology.

| Tool | Transport | Evidence |

**The pattern:** SSE for append-only server→client streams. WebSocket where traffic is
bidirectional or high-frequency. **Polling for anything that changes on human timescales** —
the entire inbox category polls, and Airflow, the largest orchestrator here, polls for
everything.

This slightly *softens* §8's recommendation: SSE for the graph and live agent state, but
**plain polling is entirely respectable for the status board.** Don't over-engineer it.

### 7.7 Who renders terminal *and* web from one model

Rarer than you'd hope, and the answers are instructive:

- **Amp (Sourcegraph)** is the clearest yes. *Agents, Everywhere* (June 2026): they rebuilt on
  **durable execution for the agent loop plus a plugin API**, and now render the same threads
  as desktop web, mobile web, and **a CLI sidebar (Ctrl+\\)**. Stated goal: *"You shouldn't
  need to juggle terminal tabs."* Note what it cost them: **a backend rewrite.** Their VS Code
  Agents Panel is keyboard-driven (`j`/`k`, `Space` to peek, `Enter` to open, `e` to archive)
  and pointedly has **no status badges** — attention is managed purely by archiving, so *"the
  displayed threads represent your working set."* That is a real, opposite design position to
  a status board. Know which one you're building.
- **Argo Workflows** renders a web UI *containing* a terminal (`xterm` ^4.19 for pod
  exec/logs), while `argo get` prints the same DAG as a tree. Same model, two renderers.
- **Claude Squad** is the pure-terminal end: Go TUI, **tmux session + git worktree per agent**,
  states `Running / Paused / Resumable`, Preview and Diff tabs.
- **Conductor** (Mac): three-pane — sidebar of workspaces, center chat, right live git diff +
  integrated terminal. A **Checks tab** aggregates git status, CI, deployments and todos
  pre-merge. Inline diff comments become composer attachments fed back to the agent.

### 7.8 ⭐ The single best structural idea in the survey: Vibe Kanban

Worth its own section because it's directly transferable and now **MIT community-maintained,
so you can read all of it**:

- Backend: **Rust / Axum + SQLx/SQLite**, crates split
  `server / local-deployment / services / executors / db / api-types`.
- **`api-types` uses `#[derive(TS)]` (ts-rs) to *generate* the TypeScript bindings** — so the
  Rust state model **is** the frontend's type model. One source of truth, mechanically
  enforced, no drift.
- Frontend: `@vibe/local-web` + `@vibe/remote-web` over a shared `@vibe/web-core` + `@vibe/ui`.
  **One core, two shells.**
- Executors implement a `StandardCodingAgentExecutor` trait normalizing 10+ agent CLIs.
- **State factoring worth copying:** `ExecutionProcessStatus` is deliberately tiny —
  `Running, Completed, Failed, Killed` — with `ExecutionProcessRunReason` as a *separate*
  semantic axis: `SetupScript, CleanupScript, ArchiveScript, CodingAgent, DevServer`. **A small
  mechanical status enum × a separate "what kind of thing is this" enum beats one giant status
  enum**, because it lets you render "setup script failed" differently from "agent failed"
  without inventing new states.

This is the architecture to copy. It is the same shape as the recommendation in this document —
one typed core, generated types, thin renderers — and it's the thing Amp had to rewrite their
entire backend to achieve.

## 8. Real-time transport

### 8.1 You already have an event bus: herdr

This is the most actionable finding in the report and it isn't a UI library at all. I
inspected the installed herdr 0.8.0 socket API directly (`herdr api schema --json`,
`herdr api snapshot`). It is far richer than the braindump's TODO list assumed:

- **`events.subscribe`** and **`events.wait`** — a real push subscription, not polling.
- **26 typed JSON event types**, including `pane_agent_status_changed` (carrying `agent`,
  `agent_status`, `display_agent`, `state_labels`, `title`), `pane_agent_detected`,
  `pane_output_changed` (with a `revision` counter), `pane_created/closed/exited/moved`,
  plus the full workspace/tab/worktree lifecycle.
- **`AgentStatus` enum: `idle | working | blocked | done | unknown`.** herdr already
  speaks the exact state vocabulary the braindump specifies. `blocked` is first-class.
- **`agent wait --until <idle|working|blocked|done|unknown> --timeout <ms>`** — block on a
  state transition, which is precisely the controller primitive from §1 of the braindump.
- **149 request commands**, including a real plugin system: `plugin.link`,
  `plugin.action.list` / `plugin.action.invoke`, and — importantly —
  **`plugin.pane.open` / `focus` / `close`**. `herdr plugin --help` describes itself as
  "Install and run **workflow** plugins."
- Snapshots already carry user-defined `state_labels` (e.g. `{"working": "RUNNING STEP 3"}`),
  free-form `tokens` (e.g. `{"flow": "alpha", "step": "3"}`), `title`, `display_agent`,
  `revision` and `state_change_seq`.

Two consequences:

1. **Your TUI should be a herdr plugin pane**, not a separate app. `plugin.pane.open` means
   the graph panel and status board can live *inside* the user's existing workspace
   alongside the agent panes. That answers the braindump's "embed or sit alongside terminal
   panes" question outright, and you write no PTY code.
2. **`state_change_seq` and `revision` are monotonic sequence numbers.** Use them as your
   SSE `Last-Event-ID`. Resume-after-disconnect is then nearly free.

### 8.2 SSE vs WebSocket vs polling

**Recommendation: SSE to the browser. Unix socket subscription (herdr `events.subscribe`)
to the TUI. Polling nowhere.**

Reasoning:

- **The data flow is overwhelmingly one-directional.** Agent state changes flow
  server→client continuously; the human clicks something occasionally. That's the textbook
  SSE shape.
- **SSE gets reconnection for free.** `EventSource` auto-reconnects and replays from
  `Last-Event-ID`. With herdr's `state_change_seq` as the event id, a laptop that slept
  through 40 state transitions catches up correctly with zero code. Doing this on a
  WebSocket means hand-rolling heartbeats, backoff, and a resume protocol — several hundred
  lines you will get subtly wrong.
- **SSE is plain HTTP.** Same auth, same middleware, same `curl` debugging as the rest of
  your API. You can literally `curl -N localhost:PORT/events` to watch the workflow state
  stream, which is a genuinely good debugging property for an agent system.
- **The classic SSE objection is obsolete.** The 6-connections-per-domain limit was an
  HTTP/1.1 problem; over HTTP/2 it's ~100 multiplexed streams. Browser support is ~97%.
- **Client→server actions should just be `POST`.** "Unblock this agent", "approve this
  step", "attach to this node" are ordinary mutations. They do not need a duplex socket,
  and making them POSTs means they're idempotent, retryable, loggable and curl-able.

**Use a WebSocket for exactly one thing:** embedded terminal panes, where you genuinely
need low-latency bidirectional bytes (keystrokes up, PTY output down). `@wterm/react` and
xterm.js both assume a WebSocket. Keep it on a separate endpoint from the state stream —
do not multiplex your workflow state through the terminal socket.

**Do not poll.** You have a push source; polling would add latency *and* load. The one
exception: a slow (30s) full-snapshot poll as a self-healing backstop against missed
events, reconciled against the SSE stream. Cheap insurance for a long-running localhost
daemon.

### 8.3 Concrete shape

```
herdr.sock ──events.subscribe──┐
                               ├──> your daemon (holds JSON/YAML workflow state)
workflow store (SQLite) ───────┘         │
                                         ├── GET  /events        (SSE, id = state_change_seq)
                                         ├── GET  /api/state     (full snapshot, for reconnect/bootstrap)
                                         ├── POST /api/actions/* (unblock, approve, retry, attach)
                                         └── WS   /pty/:pane_id  (only if embedding terminals)

TUI  ──> reads the same daemon over the unix socket (or is a herdr plugin pane)
Web  ──> React + React Flow, consumes /events
```

One state model. Two renderers. Both are dumb.

## 9. Deliverable answers, in order

**Q: Is a single codebase rendering both terminal and web actually practical in 2026, or is
two thin front ends over one JSON state model the honest answer?**

**Two thin front ends. The honest answer.** Every "one codebase" option resolves to one of
three things, none of which is what the question hopes for:

1. **Terminal-first + a transport that shoves a terminal into a browser** — Textual +
   `textual-serve`, or Ratzilla (Ratatui→WASM with a DOM backend). Real and working, but you
   get a *terminal on a web page*: no deep links, fragile fonts, no SVG graph, poor mobile.
   `textual-web` is dead (Aug 2024) and Textualize Ltd was dissolved Feb 2026.
2. **Shared component *model*, not shared components** — Ink / OpenTUI are React
   *reconcilers* with their own host elements (`<Box>` vs `<div>`). OpenTUI's own docs say
   code sharing is "very limited." You share hooks, stores, selectors and types — about 30% —
   and write every view twice regardless. That's React Native's `.web.tsx`/`.native.tsx`
   pattern, and it's fine, it's just not "one UI."
3. **Deliberately render-target-agnostic event streams** — AG-UI, whose docs say it outright:
   *"the protocol describes an event stream rather than a rendering target."* It ships web,
   terminal (Textual), Slack and Teams clients — all hand-written. **This is the strongest
   external validation of the recommendation:** the most mature project in the space chose
   exactly this architecture on purpose.

One genuine exception worth prototyping: **`ascii-dag`'s headless layout IR** (§3.1), which
can drive both Ratatui cells and browser SVG from one Sugiyama layout, with real subgraph
support. That guarantees the two views agree about topology. It's a small bet with an
outsized payoff, and it's the only true cross-surface component in this report.

---

**Q: Recommend a concrete stack, with the tradeoff stated plainly.**

See the table at the top. The tradeoff in one paragraph: **you write the board and the graph
twice (2–4 weeks of duplicated view code) and in exchange both surfaces are actually good.**
The only stack that avoids the duplication is Textual + textual-serve, and it pays for it by
making the web surface a terminal emulator — fatal for a product whose headline panels are a
graph and an inbox.

If that duplication is genuinely unacceptable, the honest fallback is **web-only first**, with
`herdr` + `agent wait` giving you a usable CLI story for free, and a TUI added later as a
second client of the same `/api/state` + `/events` endpoints. Do *not* solve it by picking
Textual.

**Q: Real-time transport, for both front ends?**

| Surface | Transport | Why |
|---|---|---|
| **Web — graph + live agent state** | **SSE**, snapshot-on-connect then deltas, `Last-Event-ID` = herdr's `state_change_seq` | One-directional, free reconnect/resume, plain HTTP you can `curl -N` to debug |
| **Web — status board** | **Polling** (2–5s) via TanStack Query | Changes on human timescales. Airflow, Temporal and Agent Inbox all poll. Don't over-engineer |
| **Web — actions** (unblock, approve, retry) | **`POST`** | Idempotent, retryable, loggable. No duplex socket needed |
| **Web — embedded terminal panes** | **WebSocket**, separate endpoint | Genuinely bidirectional bytes. Never multiplex state through it |
| **TUI** | herdr `events.subscribe` over the unix socket | Already push-based and typed |
| **Backstop** | 30s full-snapshot reconcile | Cheap insurance against missed events in a long-running daemon |

Evidence for the split is in §7.6: Argo uses SSE for watches and logs; Dagster and Trigger.dev
use WebSocket for high-frequency bidirectional traffic; **Airflow 3.x has zero WebSocket or SSE
dependencies and polls for everything.**

## 10. Suggested build order

1. **Define the typed state schema** and generate front-end types from it (ts-rs / Pydantic).
   Enforce the §5.4 rule from commit one: no presentation in the state.
2. **Daemon**: subscribe to herdr `events.subscribe`, persist workflow state to SQLite, expose
   `GET /api/state`, `GET /events` (SSE), `POST /api/actions/*`.
3. **Status board, web.** Open on a "Needs you" filter by default (Agent Inbox's
   `|| "interrupted"`). Group by template. Per-item `config` drives which of
   accept/edit/respond/ignore render. Assignability and timeouts-with-defaults from day one.
4. **TUI status board** as a herdr plugin pane, over the same endpoints.
5. **Graph panel, web** — React Flow + elkjs, as a drill-down from a board card. Add
   Langfuse's **Aggregated (template shape) vs Expanded (this run)** toggle.
6. **Graph panel, TUI** — `ascii-dag`. Prototype the shared-layout-IR idea here; if it works,
   consider retrofitting the web side onto the same IR.
7. **Terminal panes in the browser** — last, and only if genuinely wanted. `@wterm/react`.

Steps 3–4 deliver most of the value. Steps 5–7 are polish, and §7.4 argues fairly hard that
they always will be.
